# 98% 的计量与验收

用户于 2026-10-15 确认本口径：固定 .NET 10 WinForms；Windows 属性、事件、行为分别 ≥98%，Linux/macOS 对可移植能力分别 ≥98%；Windows 专属能力单列。**这是目标，不是当前完成率。**

## 固定分母

基线为本机 Microsoft.WindowsDesktop.App.Ref **10.0.11** 中的 System.Windows.Forms、System.Windows.Forms.Primitives，以及 System.Drawing.Common 的 Printing 命名空间。精确文件指纹见 [baseline.json](api/baseline.json)。首轮 804 类型只统计根命名空间；本轮纳入子命名空间与 Printing，不能把两个数字直接比较成增长或退步。

- [types.json](api/types.json)：所有导出类型，包括嵌套类型、抽象类型、枚举、委托、接口、运行时设计器契约及历史类型。
- [members.csv](api/members.csv)：逐类型有效公开/受保护成员，沿继承链展开，保留重载、访问器、参数默认值、虚方法和有关特性。Object、MarshalByRefObject 自身通用方法不作为 UI 功能分母。
- [interfaces.csv](api/interfaces.csv)：每类型实现的公开接口及其成员，包含 IContainerControl.ActivateControl、ISynchronizeInvoke、IList 等可能通过显式接口实现的契约。它们仍是公开消费面，不能因实现方法为 private 而漏掉；接口调用单列 ≥98% 门槛，不用与普通同名成员重复累加稀释分数。
- [每控件附件](README.md)：公开属性、公开事件、公开方法、构造、字段与受保护扩展分别列出；继承隐藏/覆盖优先取最派生声明。名称规范化只将 Lumina.Forms 映射到 System.Windows.Forms，不意味着二进制类型相同。
- [全类型责任映射](api/ownership.csv)：附属集合、事件参数、枚举、UIA 与历史类型均须有归属；未单独写说明页的类型不能消失。
- [完整类型到独立页映射](api/page-map.csv)：以完整命名空间及嵌套路径绑定文档，避免把 `VisualStyleElement.Button` 当成 `System.Windows.Forms.Button`；SDK 生成的 ApplicationConfiguration 单列。

生成方式：在仓库根目录运行 `./tools/compatibility/Export-Inventory.ps1`。不向解决方案增加审计产品项目，不实例化控件。默认构建 Lumina.Forms；`-SkipBuild` 只读取已有输出。基线更新须另作变更评审，不能随 SDK 升级悄悄替换。

## 分子怎样成立

属性只有在签名/类型/读写/默认值正确、创建句柄前后赋值正确、运行时变更生效、相关事件/布局/原生回读正确后才算通过。只保存字段不算支持。

事件只有在委托/参数正确，实际用户操作和程序赋值的触发规则、顺序、次数、取消效果、重入和释放后行为均有差分证据时才算通过。只声明 event 不算支持。

行为按事先冻结的场景计数，每个场景明确输入、动作、预期结果、事件轨迹和平台。至少覆盖默认状态、句柄前赋值、句柄后变更、用户输入、无变化赋值、边界/异常、释放/重建，以及该控件特有流程。方法、构造、枚举值、派生扩展独立验收，不能通过忽略它们获得“完整兼容”称号。

对每一具体控件 C、平台 P、类别 K：

`通过率(C,P,K) = 有可重现证据的通过项 / 已冻结的适用项`。

要求 **每控件** 的属性、事件、行为都达到 ≥98%；公开方法另设 ≥98% 门槛。零事件类型记“不适用”，不记 100%；只有一个事件就必须实现该事件。使用 `ceil(0.98 × 分母)` 计算最少通过数。不能用大量枚举常量、重复继承成员或简单控件拉高总分。

构造/常量/受保护派生扩展同样按各自适用项设 ≥98% 门槛；类型继承/关键接口可调用性、布局/线程/生命周期等基础兼容是先决条件，不用其他成员得分抵消。接口台账按“实际声明接口+规范化签名”归并重复继承入口后计分，同时在每个具体类型验证强制转换与调用；不以多次列出 IDisposable.Dispose 拉高比率。

全库另外报告按“声明类型+成员签名”去重后的覆盖率、控件逐项达标数、关键业务场景通过数。继承基础测试可以复用，但具体控件对继承成员的覆盖、隐藏和消息截获仍需验证。基类通过不会自动把全部派生类标绿。

## 剩余 2% 的约束

不能容纳启动失败、UI 线程错误、丢数据、错误提交/取消、资源泄漏、键盘无法完成主流程等阻塞。剩余项逐个列出 ID、原因、影响、平台、替代路径及预期版本；不允许将一整个缺失控件藏在 2% 内。

Windows 专属项在 Windows 总分母中保留。Linux/macOS 仅在有技术依据时标 `🚫平台不等价` 并列明原因，例如 HWND/WM、OLE ActiveX、桌面窗口坐标和 MDI。一般控件、绑定、字体和图像的实现困难不能自动划成 Windows 专属以缩小分母。平台判定尚未完成的项标 🔎，不能提前扣掉。

## 状态与证据

| 标记 | 含义 | 能计入通过分子 |
| --- | --- | --- |
| ✅ 代码完成 | 明确任务范围已实现，必要编译/轻量检查通过；开发部分完成 | 否，真机/兼容证据另记 |
| 🧪 验收通过 | 指定范围已有可复现的兼容验证证据 | 是，仅该范围/平台 |
| 🚧 | 已分配，正在编码 | 否 |
| 🟡 | 存在代码、签名匹配或部分实现，仍未完成验收 | 否 |
| ⬜ | 待实现或待验收 | 否 |
| 🔎 | 技术路线/平台适用性尚待验证 | 否 |
| 🚫 | 有明确依据的平台不可等价项 | 否，Windows 分母保留；其他平台按规则披露 |

文档编写完成不等于控件实现完成。各文件的“本次规划记录”与真实 Git 实现历史分开。

实施阶段使用 [tasks.csv](tasks.csv) 的 Status 跟踪开发，Verification 跟踪验收。✅ 代码完成足以继续下一开发任务，不要求提前完成复杂真机/UI测试；后期先 Windows 集中验收，再统一 Linux，macOS 真机结果单独记录。没有证据的功能仍不能计入98%。历史文档中表示清单生成、仓库整合或已运行检查的✅只证明其文字明确的范围，不等于整个控件通过。

每条验证记录至少保存 `API/场景ID、控件、平台/RID、基线版本、实现提交、用例、结果、证据路径`。生成附件保持只读快照，后续证据放独立台账，不在重新导出时覆盖验收记录。现有 77 项测试和少量探针尚未逐成员映射，**不能据此算出当前 98% 指标**；本轮所有成员运行状态保守标为未验收，不代表断言所有现有功能都不能工作。

元数据清单无法代替 C# 源码消费验证：显式接口、泛型约束、nullable、命名参数、重载解析、属性特性、事件语义、设计器序列化以及类型身份都须补验收。独立 VS 设计器程序集不是本轮运行时反射清单的完整范围；保留真实 WinForms 设计器往返作为独立发布门槛。

## 历史占位类型

.NET 10 为部分 .NET Framework 旧类型保留签名，却不提供可运行的控件；固定 10.0.11 的 [真实构造探针](../assessments/2026-10-15/legacy-control-probes.json) 验证了 DataGrid、ToolBar、StatusBar、MainMenu、ContextMenu、MenuItem 等构造抛出 PlatformNotSupportedException。这些类型仍在清单中；首先对齐基线签名、诊断及标准异常，不能把异常占位写成“旧控件已经可用”。

恢复这些类型在 .NET Framework 中的可用界面属于另行选择的迁移扩展。它们不阻塞现代 .NET 10 活跃控件的实现，也不能用大量“按基线抛异常”的成员拉高正常控件支持率。发布报告分列活跃控件逐项达标数、历史占位契约达标数及可选恢复项。具体范围和非可视依赖边界见 [补漏审计](scope-audit.md)。
